================================================================================
一、基本信息
================================================================================

YES BSL 是一个独立的兼容修复模组，用于解决 BSL Shaders 开启
"Advanced Materials" 后，某些由 native / 自定义渲染管线写入顶点的模组模型
出现「半透明闪烁」的问题。

  不做的事
  --------
  · 不修改 BSL 光影包的任何文件
  · 不修改目标模组的任何文件
  · 不使用反射
  · 不包含任何第三方的代码或资源

  做的事
  ------
  · 通过编译期 Mixin，在渲染目标几何体期间调整 Iris 对外报告的 id，
    把目标几何体引导进光影包自己预留的"跳过法线与视差"类别

  依赖（均为可选，缺失时对应部分自动失效，不会崩溃）
  --------------------------------------------------
  · Iris                    1.8+   必需，否则本模组无意义
  · Yes Steve Model (YSM)   2.x    当前针对它验证


================================================================================
二、问题背景
================================================================================

  现象
  ----
  · BSL 关闭 Advanced Materials          → 一切正常
  · BSL 开启 Advanced Materials          → 目标模组的模型半透明 + 闪烁
  · 游戏其余部分（方块、原版生物、手持物品）→ 全部正常
  · 与模型是否自带 PBR 贴图无关          → 带与不带都会出问题

  一个关键线索
  ------------
  · 手持地图时，第一人称手臂完全正常
  · 空手时，第一人称手模闪烁
  · 而两者显示的是同一份 YSM 手模

  这两者的唯一差异是「手持物品 id」，由此直接锁定根因。

三、运行原理
================================================================================

  3.1 问题的技术根源
  ------------------

  BSL 在 ADVANCED_MATERIALS 下会启用视差贴图（POM），并且——这一点才是问题的关键——
  它会用 POM 求得的坐标去采样模型贴图本身。其效果可以概括为：

      若 未命中「跳过视差」标记：
          偏移坐标 = 视差计算(原始纹理坐标, ...)
          模型颜色 = 读取模型贴图(偏移坐标)      ← 不再是原始纹理坐标

  newCoord 由 vTexCoord / vTexCoordAM 推导，而这两个 varying 又来自
  OptiFine / Iris 对 mc_midTexCoord 与 at_tangent 的语义约定
  （quad 内 UV 的仿射还原）。

  两类几何体的差别就在这里：

      几何体来源                          顶点由谁写入        扩展属性   结果
      ---------------------------------------------------------------------
      MC 标准模型（方块/原版生物/物品）   BufferBuilder      正确       POM 成立，正常
      目标模组的自定义模型                native 直接写内存  不满足前提 newCoord 偏离

  native 写入时，mc_midTexCoord 与 at_tangent 的取值不满足上述映射前提，
  于是 newCoord 偏离真实的 texCoord，采样到贴图错误的区域。

  这类模型的贴图布局紧凑、含大量空白像素，因此：

      · 空白像素的 alpha 被 alpha test 丢弃      → 看起来「半透明」
      · 偏移量随视角 / 距离每帧变化               → 「闪烁」
      · TAA 的时间累积进一步放大闪烁感

  3.2 两条完全独立的渲染路径（重要）
  ----------------------------------

  同一个几何体在不同 shader program 里，跳过视差的判据完全不同。
  这是本项目最容易踩坑的地方：

      渲染对象                 program             判据
      ---------------------------------------------------------------------
      玩家模型（第三人称等）   gbuffers_entities   entityId == 10100
      第一人称手模             gbuffers_hand       heldItemId / 100 == 4

  二者分别对应 BSL 预先留好的「跳过法线与视差」类别：

      · 实体侧：id 10100，当前包含物品展示框、画、发光物品展示框
      · 物品侧：id 400，当前包含地图

  也就是说，BSL 作者早已为「UV 布局非标准、不适合 POM」的几何体准备了逃生舱，
  本项目所做的只是把目标几何体引导进去——一行 shader 都没有修改。

  3.3 修复机制
  ------------

  在渲染目标几何体期间，让 Iris 对外报告上述 Skip 类别值：

      玩家模型：
          EntityRenderDispatcher.render  ──HEAD──▶ 建立上下文（entityId = 10100）
          CapturedRenderingState.getCurrentRenderedEntity ──HEAD──▶ 命中时返回 10100

      第一人称手模：
          IdMapUniforms$HeldItemSupplier.getIntID ──HEAD──▶ 空手时返回 400

  为什么采用「读取时覆盖」而不是「写入时改写」：
  Iris 也在同一位置写 currentEntity。若同样去改写，谁先谁后取决于 Mixin 的应用顺序，
  不可靠。改为在「读取」时覆盖则与顺序无关——读取发生在渲染过程中，
  此时上下文恰好指向被渲染的对象。

  3.4 为什么不会误伤其它光影包
  ----------------------------

  不同光影包使用各自独立的 id 空间，硬编码 10100 可能在别的光影包里
  恰好指向另一个实体类别。因此本项目不盲信硬编码值，而是运行时读取
  光影包「真实的」映射表：

      WorldRenderingSettings.INSTANCE.getEntityIds()
              .applyAsInt(new NamespacedId("minecraft", "item_frame"))

  只有当它恰好等于配置值（即这个光影包确实遵循 BSL 这套约定）时修复才生效，
  否则整体自动失效。换成非 BSL 系光影时本模组完全惰性。

  手模侧同样保守：只在「空手」时伪造，持有物品时保持真值。
  且全 BSL 中 heldItemId 只有三处真正被使用，空手时伪造 400 与真值 0 完全等价：

      · gbuffers_hand 的 skipParallax: heldId == 4        → 这是我们要的
      · gbuffers_hand 的 GetHandItem(1/2/3/50/89/213)     → 0 与 4 都不命中，结果同为 0
      · coloredBlocklight 的彩色手光: heldItemId % 100    → 0%100 == 400%100 == 0

  最后一行得益于 BSL 的 ABB 编号格式——400 的彩色光数据位恰好是 "00"，
  所以伪造它不会触发任何彩色光照。这也是 BSL 选 400 当地图类目的原因。

  3.5 性能
  --------

  CapturedRenderingState.getCurrentRenderedEntity() 会「按顶点」被调用
  （Iris 写 iris_Entity 时，以及目标模组的 native 写入器），
  因此热路径被压缩为一次 volatile int 读：

      final int overrideId = EntityIdOverride.activeOverrideId;
      if (overrideId >= 0) { cir.setReturnValue(overrideId); }

  · 不参与渲染时，代价仅为一次 volatile 读（方块、生物、粒子、GUI 等绝大多数绘制）
  · 上下文栈使用 ThreadLocal，但只在 push/pop（每个实体一次）时访问，不进入热路径
  · 无反射

  实测与未安装时相差约 1 FPS，在浮动误差范围内。

五、兼容性
================================================================================

  5.1 当前状态
  ------------

  截至 1.0.0，尚未收到任何模组冲突报告。
  以下「潜在冲突场景」为原理层面的分析，用于提示排查方向，并非已证实的问题。

  5.2 潜在冲突场景（原理分析，未实测）
  ------------------------------------

  (1) 同样注入这两个位置、且会修改返回值的模组

      本模组的两个 Iris 注入点：
          · CapturedRenderingState#getCurrentRenderedEntity
          · IdMapUniforms$HeldItemSupplier#getIntID

      若有其它模组也在这两处注入并调用 setReturnValue，则二者只有一个能生效，
      结果取决于 Mixin 的应用顺序。
      目前未发现此类模组。

  (2) 其它光影包

      本模组带「按光影包真实映射校验」的保护，非 BSL 系光影会自动失效，
      正常情况下不会误伤。可能需要注意的两类：
          · BSL 的衍生 / 改版光影：若沿用了同一套 id 约定，本模组会一并生效，
            这通常是期望行为；但也意味着它们的 Skip 类别语义会影响结果。
          · 恰好把 minecraft:item_frame 映射到 10100 却另有含义的光影包：
            理论上可能误判。如遇到，请把配置项 skipEntityId 改成 -1 即可彻底关闭。

  (3) 其它模型 / 渲染类模组

      以下模组与本模组的注入点不重叠，理论上无冲突；它们也可能存在同类问题
      （即同样由 native 或自定义管线写顶点），若出现相同症状可参考本项目的适配指引：

          · Entity Model Features (EMF) / Entity Texture Features (ETF)
          · GeckoLib 系模型模组
          · 其它基于骨骼动画的实体模型模组

          相反的，EntityCulling、ImmediatelyFast 等渲染优化模组会改变渲染时机，
          但它们不修改上述两个注入点的返回值，未发现冲突理由。

  (4) Iris / Sodium 版本变化

      本模组的 Iris 部分使用 required=false 且 defaultRequire=0 的配置：
      若 Iris 内部结构变化导致注入失败，只会静默失效，不会崩溃。
      届时表现为「修复不再生效」，请查看日志确认，并考虑更新本模组。

  (5) 其它光影管理工具

      单纯切换 / 管理光影包的模组与本项目无交互冲突。

  5.3 遇到疑似冲突时
  ------------------

  建议按以下顺序排查：

      1. 查看日志中是否有 [YES-BSL] 开头的记录，确认本模组是否正常就绪
      2. 把 config/yes_bsl.properties 中的 enabled 改为 false
         若问题消失，则可确认与本模组相关
      3. 在本模组 GitHub Issues 反馈，请附上 latest.log 与模组列表

六、配置
================================================================================

  首次启动会生成 config/yes_bsl.properties：

      # 完全关闭干预（等价于卸载本模组）
      enabled=true

      # 是否也作用于非玩家实体（为其它模组适配时可打开验证）
      affectsAllEntities=false

      # 光影包为「不适合视差贴图的实体」预留的类别 id
      skipEntityId=10100

  说明：

      enabled             设为 false 后本模组完全惰性，可用于快速排除法排查冲突
      affectsAllEntities  默认只处理玩家模型；设为 true 可测试非玩家实体是否也受影响
      skipEntityId        更换光影包时，请查该光影包 entity.properties 里
                          "跳过法线与视差"对应的编号再填入；
                          设为 -1 可彻底关闭实体侧的修复

  注意：配置文件只在启动时读取一次，改完需要重启游戏才生效。
        （这一点与同目录的 YES-SB 不同，那个支持热重载。）


  关于「注入失败」的两种严格程度（刻意不同）

      配置                          目标                        失败后果
      ------------------------------------------------------------------------
      yes_bsl.mixins.json           MC 自己的                  直接报错
                                    EntityRenderDispatcher     (required=true,
                                                               defaultRequire=1)
      yes_bsl.iris.mixins.json      Iris 的内部类              静默失效
                                                               (required=false,
                                                               defaultRequire=0)

      前者刻意做成硬失败：本模组的唯一功能就挂在这一处，靶点签名在大版本内
      非常稳定；一旦对不上（例如换 Minecraft 大版本），明确报错远比
      "悄悄什么都不做"更好排查。

      后者相反：Iris 的内部结构变动更频繁，且光影相关的失败不该拖垮游戏，
      因此做成软失败。

      若看到 EntityRenderDispatcher 相关的 Mixin 报错，说明本模组与该
      Minecraft 版本不兼容，请先移除它或等待适配版本。

七、已知限制
================================================================================

  · 修复生效后，目标模型会失去「视差贴图(POM)」「自阴影」「PBR 法线扰动」三项
    效果——这三者同属 POM 体系，是无法分离的。

    但 PBR 的「平面视觉效果」全部保留：
        金属度、光滑度、f0、自发光、次表面散射、环境光遮蔽、镜面高光、SSR 反射
    （因为它们来自 GetMaterials()，不受 skipParallax 影响）

    对于体素块拼出的 3D 模型，失去的这三项在视觉上通常不可察觉。

  · 当前仅针对 Yes Steve Model 验证。其它模组若存在同类问题，
    需要按其渲染路径做少量适配（见 README 的「为其它模组适配」一节）。

  · 手模侧的伪造条件目前限定为「空手」。若某个模组在持有物品时
    也渲染自定义手部模型，那一场景本模组不会介入。

  本项目的依赖关系刻意做得松散，便于他人适配与二次开发：

  这两个文件是适配新模组时的主要改动点，其余机制可以原样复用。
  详细指引见 README 的「为其它模组适配」一节。

  欢迎提交其它模组的适配、冲突报告与改进建议。
